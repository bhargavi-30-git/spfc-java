## Version and Currency Rules

Because technology evolves, follow these rules:

1. Verify all version-sensitive claims against current official documentation.
2. Prefer official documentation, specifications, release notes, JEPs, and project repositories.
3. State the exact date on which version information was verified.
4. Separate stable recommendations from experimental ones.
5. Do not invent version numbers.
6. Do not silently assume compatibility between Java, Spring Boot, Spring Framework, Spring Security, Spring AI, Hibernate, Gradle, Maven, or other tools.
7. Create an explicit compatibility and modernization matrix.
8. Label technologies as:
   - Essential now
   - Important for legacy maintenance
   - Useful specialization
   - Optional
   - Emerging
   - Deprecated
   - Removed
9. Mention replacement technologies or migration paths for deprecated approaches.
10. Explain why an organization might still use older versions.
11. Recommend a primary learning baseline for new projects.
12. Recommend separate baselines for reading or maintaining Java 8 and Java 17 applications.
13. Explain how the learning plan should adapt if Java 25 or a related framework is not yet appropriate for production use in a learner's environment.
14. Use exact framework names and distinguish similarly named projects.
15. Avoid relying on blogs when authoritative project documentation is available.
